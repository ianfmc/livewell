## Problem

Turn US congressional/executive financial disclosures into a per-instrument
daily feature for LIVEWELL, and test empirically whether it improves the
model. Raw data is per-member **equity** trades; LIVEWELL trades a mixed
universe (forex, stock indices, metals, energy). The design must bridge that
gap honestly — exploit strong links, don't force weak ones.

## Instrument universe (already ingested — `livewell/ingestion/constants.py`)

19 instruments across three classes:
- **Indices:** US 500 (^GSPC), NASDAQ 100 (NQ=F), Russell 2000 (RTY=F), Dow Jones (YM=F), Nikkei 225 (NKD=F)
- **Metals/energy:** Gold (GC=F), Crude Oil (CL=F), Natural Gas (NG=F)
- **Forex:** EUR/USD, GBP/USD, USD/JPY, AUD/USD, AUD/JPY, EUR/JPY, EUR/GBP, GBP/JPY, USD/CAD, USD/CHF, USD/MXN

This universe is the reason the signal is viable: congressional equity trades
map **near-directly to stock indices**, moderately to commodities, weakly to forex.

## Decisions (this session)

- **Bridge = sector/index rollup, per-instrument routing (option A).** Map each
  disclosed ticker → sector → the LIVEWELL instrument(s) it informs. Tech-heavy
  buying → NASDAQ 100 / US 500; broad → Dow / US 500; small-cap → Russell 2000;
  energy-sector → Crude Oil / Nat Gas; materials/miners → Gold. Forex and Nikkei
  get **no direct feature in v1** (deferred to a later macro-proxy tier — option C).
  *Rejected B (single global buy/sell scalar): throws away the sector structure
  the indices can exploit. Rejected C-now (two-tier with forex macro proxy): correct
  end state, but build the strong links first and prove them before the weak ones.*

- **Ticker→sector→instrument map = curated, version-controlled lookup (option B).**
  A committed CSV covering the few-hundred tickers Congress actually discloses.
  *Rejected full GICS/index-membership feed: licensing + overkill before the signal
  is proven. Rejected yfinance `.info` at runtime (option C): a live probe this
  session confirmed sector labels are fine for large-caps BUT ETFs/funds return
  `sector=None` (coverage holes), yfinance carries no index-membership data (so the
  sector→instrument routing is hand-built either way), and a scraped endpoint is a
  flaky dependency in a daily Lambda's hot path. Optional: use yfinance offline,
  once, to SEED the curated CSV — then commit it — getting C's speed without C's
  runtime risk.*

- **Recency weighting with decay.** Recent trades weighted higher; older trades
  decay but are not dropped ("echoes / long-term implications"). Exact half-life
  is a tuning parameter, set during the ablation, not fixed now.

- **Accept/reject gate = ablation.** Compare model outputs and score distributions
  **with vs without** the congressional feature, on the **same walk-forward folds**
  as the Phase 2 LR baseline. Report per-instrument-class (indices vs commodities
  vs forex) so we can see *where* the signal helps. If it doesn't beat baseline on
  win rate and/or EV without hurting calibration/stability, it is not promoted.

## Architecture fit (no change to existing design)

Matches the settled five-layer pipeline and S3/DynamoDB split:
1. **Daily ingestion Lambda** — pull disclosures from a community pipeline (do NOT
   hand-write House/Senate parsers). Source pinned at implementation (see ADR-0001).
2. **Normalize → CSV on S3** — one clean row per disclosed transaction, under the
   analytical S3 layer (e.g. `raw/congress/`, `curated/congress/`).
3. **Rollup + join** — apply the curated ticker→sector→instrument map, aggregate
   with recency weighting to a per-instrument daily feature, join to existing
   curated feature rows on (instrument, date).
4. **Ablation** — feed/withhold the feature in the existing walk-forward training.

## Data reality (from ADR-0001 + this session's verification)

- No single official machine-readable feed. Three systems: House Clerk FD portal,
  Senate eFD, OGE (executive). STOCK Act lag: 30 days (Senate) / 45 days (House),
  often longer. Data is equity-focused, lagged, sparse.
- Community pipelines exist (Senate-only scrapers; House+Senate aggregators; hosted
  services). Reliability/license must be verified before pinning one.

## Open questions (for plan / implementation, not blocking the ADR)

1. **Lag vs lookback:** given 30–45+ day filing delay, what feature lookback window
   avoids lookahead leakage while still capturing "echoes"?
2. **Join granularity:** confirm the feature is per-(instrument, date), with unmapped
   tickers bucketed "other" and excluded from routing.
3. **Sequencing:** ADR-0001 recommends deferring implementation until Phase 4 core is
   verified operational and the LR baseline is reproduced. Confirm.
4. **Source pin:** which community pipeline (aggregator vs House+Senate extractors),
   with license + update-cadence recorded.
